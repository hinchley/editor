# Style

How code in `src/` is written. `.clang-format` handles layout: run `clang-format -i src/<file>` (version 22 or later) on anything you write. This file covers what clang-format cannot check. ARCHITECTURE.md's Conventions section covers the build (C23, strict warnings, vendored code).

`src/unicodedata.c` is generated by `tools/unicodedata.py`, and `vendor/` is not edited, apart from the patches recorded in `vendor/patches/` (see ARCHITECTURE.md, The default packages). `.clang-format-ignore` skips both.

## Layout clang-format does not enforce

- **Width:** 95 columns for code and comments.
- **No braceless body on the next line.** A short body goes on the line of its `if`, `else` or loop. A body that does not fit there gets braces. clang-format would move it to the next line without them, so add the braces yourself:
  ```c
  if (!count) return false;
  else if (wrapped) *wrapped = true;

  if (diagnostics->items[index].severity < diagnostics->items[*worst].severity) {
    *worst = index;
  }
  ```
- **Case labels** are indented inside their switch, and a body always goes on the lines under its label, however short it is. clang-format does this.
- **Long signatures and calls:** when they don't fit, put one parameter or argument per line, indented two spaces, with the `)` on a line of its own. A function's `{` still goes on the next line:
  ```c
  static bool
  FindForward(
    const MatchSet *set,
    Position from,
    bool *wrapped
  )
  {
  ```
- **`// clang-format off` / `// clang-format on`** guards only two kinds of code: packed numeric tables (`inflate.c`, `jpeg.c`), and string literals whose indentation shows structure (the JSON in `lsp.c`, the commented escape sequence in `term.c`). Code inside the guards still follows the rules here.
- **Multi-line ternary chains** break before `?` and `:` and are aligned (clang-format does this).
- **Braced initialisers** follow clang-format. One that fits goes on one line. One that fits on the next line breaks after the `=` and is indented two spaces. Otherwise it opens with `= {` and has one item per line:
  ```c
  Save save =
    {.file = file, .buffer = buffer, .message = message, .overwriteChanged = overwriteChanged};
  ```
- **Record tables** (bindings, names and kinds, key labels) have one record per line. A record that does not fit has one field per line.
- **Never write a trailing `,`** in an initialiser, enum or argument list.
- **Blank lines:** one between functions, and one after a run of guard clauses or between steps of a function. Never two in a row, and never one at the start or end of a block.

## Naming

- Types and functions are `PascalCase`. Variables, fields, parameters and constants are `camelCase`. Nothing uses `snake_case` or `ALL_CAPS`, except libc and tree-sitter names.
- A public function starts with its module's name, or with the name of the type it works on (`BufferReplace`, `StrBufAppend`, `PositionCompare`, `DiagnosticSeverityName`). A `static` function has no prefix (`FreeLines`, `ReadPosition`).
- An enum constant starts with its enum's name (`ServerSyncFull`, `LayoutKindTab`). If an enum needs a count, end it with a `...Count` constant.
- Use whole words, not abbreviations: `index` (never `i`), `count`, `capacity`, `length`, `position`, `buffer`, `context`. Name a boolean as a fact (`opened`, `wantsSave`, `lineWise`).
- Callbacks are named for the event: `...Done` for an answer, `...Answered` for a prompt, `...Picked`, `...Visit`. The `void *context` comes first.

## Types and declarations

- **Numbers:** use `i8`–`i64`, `u8`–`u64`, `f32` and `f64` from `types.h`. Use `int` only where libc requires it: `main`, signal handlers, `qsort` comparators, and `%.*s` widths. Sizes, lengths and byte offsets are `u64`.
- **Structs:** `typedef struct Name { ... } Name;`, always with the tag. A one-off table may use an anonymous `static const struct { ... } name[] = {...};`.
- **Enums are not typedef'd.** Write `enum ServerState state;` wherever one is used.
- **Constants:** `static constexpr` with a type, never `#define`. The code has no macros. Settings live in `settings.h`.
- Mark unused parameters `[[maybe_unused]]`. Don't cast them to `(void)`.
- **Literals:** `nullptr` (never `NULL` or `0`), `{}` to zero (`StrBuf text = {};`, `*buffer = (Buffer){};`), digit separators in large values (`10'000`), uppercase hex (`0x7F`), and lowercase suffixes (`100ull * 1024`).

## Idioms

- Test truth directly: `if (!count)`, `if (!document)`. Compare with `!= nullptr` only to return a `bool`.
- Return early from guard clauses, and use `continue` to skip loop items, rather than nesting.
- Cast every narrowing or sign-changing conversion explicitly (`(u64)(end - at)`), because `-Wconversion -Werror` is on.
- Always write `sizeof` with parentheses: `sizeof(x)` and `sizeof(Type)`.
- Use `x++` (postfix) as a statement.
- Allocate with `MemoryResize(pointer, count, size)` and free with `free`. Grow by doubling from a small start (`capacity ? capacity * 2 : 16`); a `StrBuf` grows by half, since edits grow lines in place. Only `memory.c` calls `malloc`/`realloc`, and allocation failure ends in `Fatal`.
- A function that can fail returns `bool` (or a status enum), and appends a reason to a `StrBuf *message`/`error` that it is given.
- Put a forward declaration only where recursion needs one, laid out like any other declaration. Otherwise define a helper above its first use.
- A small accessor in a header is `static inline`.

## Comments

- Use `//` only. Write lowercase prose that ends with a period. An identifier keeps its own case (`// UINT64_MAX when there is none.`).
- Start every sentence on a new line, never partway through a line. Wrap a long sentence onto the next line, within 95 columns.
- Put the comment above what it describes. Don't put comments at the end of a line, except to annotate the pieces of a concatenated escape sequence.
- Say what something is or does, not how:
  - a function that returns a value is described by a noun phrase (`// the position after the last byte.`);
  - one that acts, by a verb in the third person (`// replaces range with text ...`).
  Name parameters plainly, without `@param`. State edge cases and ownership: `// the text pointers are only valid while the listener runs.`
- Comment a struct field or enum constant above it when its meaning is not obvious. Use a blank line to group related fields.
- Write `nullptr`, `utf-8` and `json` in comments as they are written in code.

## Files

- **Header:** `#pragma once`, a blank line, a comment saying what the module is, then its includes with no blank line between. Then types, and declarations, each with its comment unless the name says it all.
- **Source:** its own header first, a blank line, the `<system>` headers sorted, a blank line, the `"local"` headers sorted. Then file-scope constants, types and `static` state, then the functions.
