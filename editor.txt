# Terminal Text Editor Requirements

## Goal
Create a custom terminal text editor that is tailored to my personal needs. It should not include features simply because they are "standard" in other editors, or likely to be expected by other people.

## General
- Linux x64 only (e.g. no Windows, no WSL).
- Modern terminal emulators only (specifically foot, alacritty, ghostty, and kitty).
- Wayland only.
- Uses cfmakeraw for enabling raw mode (and uses an alternate screen).
- Dynamically responds to terminal resize events via SIGWINCH signal.
- Terminal size is determined via a POSIX system call (not escape sequences).
- Cursor position is determined via a standard VT command (cursor position report).
- Implements Kitty Keyboard Protocol (no legacy mode fallback).
- Written in C (latest standard).
- Named: editor

## Usage
The following usage is supported:
- editor. Runs the editor and opens a new empty buffer.
- editor file1. Runs the editor and opens an existing file named file1 or a new empty buffer, which when saved, will create a file named file1.
- editor file1 /path/to/file2. Runs the editor and loads file1 and file2. Shows the file picker so the user can select which file to open.
- editor folder1. Runs the editor and loads all files (at any depth) under folder1. Shows the file picker so the user can select which file to open.
- editor folder1 /path/to/folder2. Loads all files under folder1 and folder2 (at any depth). Shows the file picker.
- editor file1 folder1. Loads file1 and all files under folder1 (at any depth). Shows the file picker.

A few notes:
- Files in folders are always lazy "opened". i.e. They are added to the buffer list, but only read into memory when first used.
- .git folders are never loaded. No attempt is made to limit what is loaded via content of .gitignore files.
- There is no limit on the number of files/folders that can be specified on the command line.
- There is a hard limit on the maximum number of files that can be loaded: 100,000. The editor will not start (not even switch terminal modes) if that number is exceeded. A suitable error message will be displayed. This limit is enforced if a user attempts to create or load additional files after the editor is running. In this case the operation is refused and a suitable error message will be displayed in the editor message bar.
- There is a max file size limit. Suggest 100MB. Files exceeding this limit will not be opened, although they will be loaded. A suitable error message will be displayed in the editor message bar.
- Symlinked sub-folders are not loaded. Symlinked files are loaded.
- Binary files are loaded but not opened. An attempt is made to determine if a file is a binary file when the file is first used (nul character present in first 4K). If determined to be a binary, a suitable error message will be displayed in the editor message bar.
- No other command line arguments. No --help. No --version. The only supported command line arguments are an optional list of files and folders to load.

## Configuration
There is no global config file. Settings are baked into the source code (using named values that are easily identified and changed if needed).
However, the editor does respect folder-based configuration files (stored as .editor). i.e. When opening a folder (or sub-folder) the settings within any detected .editor file are applied to all files within that folder (and all sub-folders). Nested .editor files replace parent .editor files (they are not cumulative). .editor files are only processed when the editor is opened (not when they are added/edited).
An .editor file is exclusively used to filter the files that are loaded by the editor.
The syntax is as follows:
foo.txt  # matches files at any depth with this exact name
*.c      # matches files with a .c extension at any depth
bar/     # matches folders (and all contents) at any depth with this exact name
/foo/foo.txt # matches a file with this exact path (relative to the .editor file)
/*.c     # matches files with a .c extension in the same folder as .editor
/bar/    # matches a folder (and all contents) with this exact path (relative to the .editor file)

## Settings
Although there is no global configuration file, the following should be easily modifiable in the code:
- tabWidth. Measured in columns. Set to 2. Not dynamically modifiable.
- softWrap. Wrap long lines to the window width. Set to false. Can be toggled dynamically.
- scrollOffset. Rows and columns kept between the cursor and the window edge: the view scrolls before the cursor gets closer than this (0 scrolls only at the edge). The margin yields at the start and end of the buffer. Set to 4. Not dynamically modifiable.
- lineNumbers. Show the line-number gutter. Set to true. Can be toggled dynamically.
- cursorStyle. Defines the cursor shape. Either vertical line or block. Set to line. Not dynamically modifiable.
- cursorBlink. Determines whether the cursor blinks. Set to true. Not dynamically modifiable.
- showWhitespace. Render spaces and tabs as faint symbols. Set to true. Can be toggled dynamically.
- ruler. Draw a thin vertical guide line (just after the column specified at rulerColumn). It is purely visual and never affects typing or soft wrap. Set to false. Can be toggled dynamically.
- rulerColumn. Sets the column used when ruler is enabled. Set to 100. Must be between 0 and 500. Can be changed dynamically.
- expandTab. Insert spaces (up to the next tab stop) instead of a tab character. Set to true. Can be changed dynamically.
- trimTrailingWhitespace. Strip trailing whitespace from every line when saving. Set to false.

## Key Features
A non-exhaustive list of features are presented below. Others are implied from shortcuts.
- Multiple files/folders with buffer switching. Includes an interactive sub-string match buffer picker. Also includes a picker for selecting between unsaved files.
- Multi-level undo/redo. Insert/delete/replace operations are symmetric. Consecutive typing/backspace/delete coalesce into one change, broken by any cursor movement. A multi-cursor edit is wrapped in one grouped transaction that undoes and redoes in a single step.
- Tree-sitter syntax highlighting for C, HTML, CSS, JSON, JavaScript and Markdown (the last with language injection, so fenced code blocks and inline spans are highlighted). See below for more detail.
- Multiple cursors. With every edit from multiple cursors treated as a single undo step. Each cursor uses the configured cursor style.
- Incremental search (every match highlighted, with next/previous, and case sensitivity toggle), also with interactive replace, replace-all, and both with support for backslash escapes (e.g. \t).
- Editor-wide search (across all loaded buffers) with a split panel layout for displaying matches. See below for more detail.
- Full unicode UTF-8 support (navigating and editing).
- Smart indentation. This includes being able to indent a block of selected text by pressing tab.
- Language aware commenting (file type determined from extension); only supported for the languages covered by tree-sitter.
- A searchale shortcut list. See below for more detail.
- Copy/cut/paste with system clipboard integration (wl-copy/wl-paste).
- Line number gutter.
- Soft-wrap.
- Whitespace display.
- Dynamic reflow of text on terminal window resize.
- Side by side editing. A single vertical split showing two equal-width buffers.
- A persistent status bar showing the following left aligned: file name (with [+] for unsaved changes) and the following right aligned: soft-wrap status, file type (if known), line ending format, row:column, total lines, open buffer count:total buffer count.
- A message bar below the status bar that reports results from the past operation. It is used to both collection user input when performing a command (e.g. search term when pressing Ctrl+F) and also to report the result of a command (e.g. number of matches).
- Spell checker. Uses a plain sorted text file (one word per line). This is available under `data/words.txt` and is compiled into the binary. Spell check is invoked via shortcut on demand against current buffer. Words in the document which are not in the word list are highlighted using same behaviour as Ctrl-F. i.e. can navigate between matches in the same way. this includes returning to past matches with Alt+N, Alt+P.  Note: URL for word list (still contains header: https://app.aspell.net/create?max_size=60&spelling=AU&variant_level=4&diacritic=both&special=hacker&special=roman-numerals&download=wordlist&encoding=utf-8&format=inline).

Line endings are detected when a file is loaded (CRLF or LF; a mixed file is based on the most common) and shown in the status bar. The text is edited as plain
`\n` lines, and the detected ending is written back on save, so a CRLF file stays CRLF. Alt-E switches the buffer between the two and marks it modified.
Pasted CRLF text is normalised the same way. New files use LF.

## Shortcuts
Press Alt-H at any time for a filterable list of every binding. Key summary:
- Move: arrows / Home / End / PageUp / PageDown; Ctrl-Left/Right by word; Ctrl-Home / Ctrl-End to the start / end of the file. Home is smart: it jumps to the first non-blank column, or to column 0 when already there.
- Ctrl-Up / Ctrl-Down: scroll the view one line without moving the cursor (it stops when the cursor would come within the scroll margin of the edge).
- Select: Shift + any movement key (incl. Ctrl-Shift-Left/Right by word and Ctrl-Shift-Home/End); Ctrl-A selects the whole file.
- Edit: typing, Enter (indent-aware), Tab, Backspace, Delete, Ctrl-Backspace deletes the previous word.
- Ctrl-Z / Ctrl-Y: undo / redo.
- Ctrl-C / Ctrl-X / Ctrl-V: copy / cut / paste (system clipboard via wl-clipboard, with an in-process fallback).
- Ctrl-Shift-Up / Ctrl-Shift-Down: move the current line, or every line the selection touches, up / down as a block.
- Ctrl-D: duplicate line; Ctrl-K: delete line.
- Ctrl-M: extend selection to all text inside the closest pair of matching brackets (if any).
- Alt-M: jump to matching bracket; Ctrl-W: jump to the next occurrence of the word under the cursor; Ctrl-/: toggle line comment.
- Alt+S: initiate spell check against the current open buffer. Unknown spellings are highlighted similar to the approach used by Find.
- Ctrl-E: multiple cursors - select the word under the cursor, then add a cursor at each next occurrence; type to edit them all at once (a single undo step).
  Ctrl-Alt-Up/Down add a cursor on the line above/below; Esc collapses back to one cursor.
- Ctrl-N: new buffer (prompts to save the current one if it has unsaved changes); Ctrl-O: open an existing file (new buffer) or folder (replaces all, after a save prompt); Alt-R: reload the current file from disk (prompts if there are unsaved changes); Alt-E: toggle the file's line endings between LF and CRLF.
- Ctrl-PgDn / Ctrl-PgUp: next / previous buffer; Ctrl-Tab: last-used buffer; Ctrl-P: sub-string buffer picker; Ctrl-U: pick from buffers with unsaved changes.
- Split view: Ctrl-Alt-Right splits the window into two side-by-side views of the current buffer; Ctrl-B splits and opens a new empty buffer in the new view (both need a window at least 80 columns wide and no existing split). Ctrl-J moves focus to the other view, Ctrl-T swaps the two sides, and Ctrl-H closes the focused view (the buffer stays open; nothing is prompted). Every other command acts on the focused view, and the same buffer can be shown in both: edits appear in each at once, while the cursor and scrolling are independent. Pickers and prompts span the full window. The focused view shows the full status bar (the other is dimmed, with just its file name) and owns the cursor. Display toggles (wrap, line numbers, whitespace, ruler) apply to both views.
- Ctrl-F: incremental search (type to filter; ↑/↓ or Ctrl-N/Ctrl-P between matches; Ctrl-T toggles case sensitivity; Enter keeps the match, Esc cancels). Supports escape characters and ^ and $ as per Ctrl-R.	 
- Alt-N / Alt-P: next / previous match of the last search.
- Ctrl-Shift-F: search every open buffer (open a folder first to search a project). After the text it asks which files to search ("in files"): blank for all, or space-separated globs: `*.c *.h` (by file name), `src/` (a folder), `src/*.c` (a path), and `!` to leave files out (`*.c !test*`). This is effectively the same syntax used by .editor but with the inclusion of ! to leave out files. The prompt starts with the last scope, so Enter repeats it; files outside the scope are not even read. With no hits it says so; otherwise a list of `file:line` appears beside a preview of the lines around the highlighted hit (the preview needs a window of 80+ columns; narrower shows just the list). Enter opens that hit. The list is kept: Alt-F brings it back, starting after the hit you last opened, and Esc in the list clears it.
- Pickers (help, buffers, search results): Up/Down, PgUp/PgDn, Home/End; type to filter. A filter matches substrings, and `^` at the start and `$` at the end anchor it and make it literal (`^src/`, `.c$`, `^a.h$`). Long paths are shortened in the middle with `...`.
- Ctrl-L: go to a line, or `line:col` (e.g. `42:10`).
- Ctrl-R: search & replace (enter pattern, then replacement, then step through with `y`/`n`, `a` for all, `q` to stop). Both the pattern and replacement understand the escapes `\t`, `\r`, `\\` (e.g. replace `\t` with a space); `\n` is accepted but never matches, since a match cannot cross a line break.
- Alt-T: toggle inserting spaces for tab; Alt-W: toggle soft wrap; Alt-L: toggle line numbers; Alt-.: toggle whitespace display; Alt-G: toggle the vertical ruler; Ctrl-G: set the ruler column (1–500) and show the ruler.
- Ctrl-S: save (prompts for a name when the buffer is unnamed); Ctrl-Shift-S: save every modified buffer; Ctrl-Q: quit (offers to save all buffers with unsaved changes).

## Syntax Highlighting (Detailed)
Highlighting is not baked into the core editor. The runtime and grammars for C, HTML, CSS, JSON, JavaScript and CommonMark (Markdown, via its block + inline grammars) are vendored under `vendor/` as C sources and compiled straight into the binary. There is no external runtime dependency. Each grammar's highlight query is embedded into the binary at build time (via C23 `#embed`). The language is chosen from the file's extension; a file type with no grammar simply renders uncoloured.

Markdown exercises language injection: a fenced code block is re-parsed and highlighted with the grammar named by its info string (e.g. ```c), and inline spans (emphasis, links, code) with the inline grammar. Any injected language that isn't vendored simply stays uncoloured.

`src/highlight.c` is the only place the editor knows about languages: it parses the buffer, re-parses incrementally on each edit, runs the query over just the visible window each frame, and resolves overlapping captures into colored spans. `src/theme.c` maps tree-sitter capture names (e.g. `keyword`, `string.special`, `function.builtin`) to highlight groups and each group to a 256-colour SGR code. Two groups colour the UI rather than syntax: `gutter` (the line-number gutter) and `whitespace` (the faint space/tab symbols).

A capture is coloured by the group sharing its first component — `string`, `string.special`, and `string.special.key` all use the `string` group, and any `*.builtin` capture uses `builtin`.

This is the suggested syntax highlighting theme:

### Adding a language
1. Obtain the grammar's generated `src/parser.c` (and `src/scanner.c` if it has one) from the grammar repo's `src/`, or by running `tree-sitter generate`, and drop them into `vendor/grammars/<lang>/` along with the grammar's `src/tree_sitter/` headers. Copy its `queries/highlights.scm` into `vendor/queries/<lang>/`.
2. Add one row to the `grammars[]` table in `src/highlight.c`: the language name (matching the display name in `src/lang.c`), an injection id (the lowercase identifier other grammars inject it by, e.g. `c`), its `tree_sitter_<lang>()` entry point (declare it alongside the others), an `#embed` of the new `vendor/queries/<lang>/highlights.scm`, and — only if the language embeds others — an `#embed` of a `vendor/queries/<lang>/injections.scm`. Injections name the child by its injection id, so a newly-added grammar is immediately usable inside a fenced code block.
3. If the extension isn't already mapped, add a row to `langTable` in `src/lang.c` (extension → name + line-comment token).
 
## Compilation
- Use build.sh
- Use gcc with a strict warning set (`-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Werror`). must build with zero warnings.
- No tests.
 
## Code Format
- Do not allow code to exceed 95 character width.
- Write functions in this format:
void
FunctionName(char *a)
{
}
or in header:
void
FunctionName(char *a);
- Ensure comments begin with // and are in lowercase.
- Keep main.c minimal. It should do little else than initiate a call to bootstrap the application.
- Divide functionality into small, suitably named, loosely coupled modules with clear and well defined interfaces.
- Variables should use camelCase (no underscores). Functions PascalCase.
- Keep functions small. Try to avoid functions with over 100 lines of code. Be pragmatic. This is not a hard rule.
- Try to organise functions logically within a file, and aim to limit the use of forward declarations where possible.
- Code blocks like those in conditionals, loops, etc, should follow this format:
if (x == y) {
  // do somethinig
} else {
  // something else
}
- If all blocks are only a single line (and fit within line width constraints), this is preferred:
  if (x == y) do something
  else something else;
- Do not do this:
  if (x == y) do something
  else {
    something else;
  }
- Create a types.h that defines an alias for all fixed width integer types. e.g. u8, i16, i32, etc. Only use these in the code base.
- Remember the target is x64 Linux (use -D_DEFAULT_SOURCE). Don't cater for other platforms or systems.
- Add empty lines before and after code blocks. e.g. don't stack if statements (with blocks) directly on top of one another. Allow the code to breathe.
- Try and minimise the number of parameters passed to a function. Consider the use of structs for this purpose if that is helpful.
- If a function call is too large to fit on a single line, structure it like this:
  foo(
    arg1,
    arg2
  );
  Use a similar approach when defining a function:
  int
  foo(
    char *arg1,
    char *arg2
  ) {
   
  }
- Don't use trailing commas in lists (e.g. arrays, structs, etc).
- Avoid macros where possible. Only consider in special circumstances where they add considerable value.
- Feel free to add helpful comments in the code that explain useful context or which clarify the task that is being performed.
- When writing comments, don't be verbose. Don't use emdashes. Try to start new sentences on a new line. Avoid this:
  // this is a comment. and
  // this is another.
  Instead:
  // this ia a comment.
  // and this is another.
- Think carefully about naming of identifiers. Try to be consistent in terminology. Prefer simple and clear names. Functions defining the public interface of a module should share a common prefix. e.g. editor.c might expose EditorClose and EditorOpen.
- Prefer complete words for names rather than truncated words (unless this starts to impact code wrapping). e.g. length instead of len. count instead of cnt. index instead of idx.
- Consider the most pragmatic memory management system. This may involve distributed use of malloc, or an arena, or something else. The key is to keep the code simple and clean.
- Adhere to a well considered loosely coupled architecture with clear separation of concerns. But avoid unnecessary abstractions or bloat.
- Initial testing has suggested that a single flat array of "lines" - each a growable utf-8 byte buffer - is sufficient for providing adequate performance when editing large text files (several MB in size). I am happy to stick with this approach unless you think significant performance benefits or other improvements are to be gained by using an alternate strategy (gap buffer, piece buffer, etc). Again, be pragmatic. The code needs to be clear and simple.
- Architect the solution so that tasks such as movement and scrolling is written once for both wrapped and unwrapped views.
- As mentioned above, files should be lazy loaded to minimise the performance impact of working with a large collection of files. In general, try to avoid unnecessary processing overhead associated with loaded files that are not active, or if active, are not currently visible (not an active buffer).
- Do not use any third party dependencies other than that described for tree-sitter.
- Produce a clear and pragmatically authored README.md. Also produce an ARCHITECTURE.md document that outlines the solution architecture. Markdown documents should not use hard wrap for long lines.
- You may use test cases as needed to develop the code, but I do not want to maintain them in the code base.
- Don't use make or any other build system. Wrap the use of gcc via build.sh.
- If the same abstractions are needed in multiple locations in the code base (e.g. string buffer) - pull this code into its own module and reuse it.
- When working with low level identifiers, such as numbers that represent cursor styles, use enums or other named identifiers rather than raw numbers.
- Don't use underscores in module names.
- Store all source files (other than tree-sitter vendor code) under src (one flat folder containing both .c and .h).
- Use the built-in bool from c23.
- Create a .clangd appropriate for the codebase for use in the Zed editor.
- Ensure errors are captured and surfaced appropriately. e.g. Don't silently allow potential memory allocations to go unhandled.
- Finally, this solution will be used exclusively by me. It is not intended for use by others. So standard conventions that might be expected by others are not strictly necessary. Everything should be included by merit based on the intended target and usage.
