# Architecture

This document describes how the editor is put together.

## Layout

| Path | Contents |
|---|---|
| `src/` | All editor sources, flat, `.c` and `.h` together. |
| `vendor/tree-sitter/` | Tree-sitter runtime (`include/`, `src/`). Compiled through its `src/lib.c` amalgamation. |
| `vendor/grammars/<id>/` | Generated grammar sources (`parser.c`, optional `scanner.c`) and their `tree_sitter/` headers. PHP and XML keep upstream's layout (`php/src/`, `common/scanner.h`) because their scanners include a shared header by a relative path. |
| `vendor/queries/<id>/` | `highlights.scm` and, where the grammar embeds other languages, `injections.scm`. |
| `languages/<id>/` | The editor's own files of each default package (see Languages): its `language` file and, for a language with symbols, `tags.scm` (see Symbols). Not vendored, so they are edited freely. |
| `data/words.txt` | The default spell check word list, one word per line, sorted in byte order (`LC_ALL=C`). Not built in: `build.sh --install` copies it to the config folder when there is no list there (see Spell check). |
| `tools/` | Scripts that are not part of the binary: `unicodedata.py` generates `src/unicodedata.c`, `bindings.py` writes the key binding tables in README.md from `src/keymap.c`, and `language.sh` makes a language package from a grammar repository. |
| `build.sh` | The build. Outputs `./editor`, objects go to `build/`, and with `--languages` the default packages go to `build/languages/<id>/`. `--install` puts them and the word list in the config folder. |

## Glossary

- **Loaded**: a file is in the buffer list.
- **Open**: a loaded buffer whose contents have been read into memory. Files from folders are loaded at startup but only opened when first used.
- **Display column**: a 1-based screen column within a line, with tabs expanded and wide characters counted as two. Used by the status bar, go to line and the ruler.

## Data flow

The editor is one thread around one loop in `app`:

1. **Input.** `TermWait` polls standard input and the resize pipe. `input` decodes the bytes into events: keys, pastes and terminal replies.
2. **Dispatch.** A running scan (project search or indexing symbols), learning mode, an open picker, the find and replace prompts and any other prompt take a key first, in that order. Otherwise a printable key is typed, and any other key is looked up in `keymap`, whose command `app` runs.
3. **Commands** live in the modules that own what they change (`move`, `edit`, `search`, `session`, `save`, `project`). They work on the current document's focused view through `workspace`, and change text only through `BufferReplace`.
4. **Listeners.** Every replace notifies the buffer's listeners: both views of the document (cursors and scroll position), its undo history (records) and its highlighter (tree edits). Nothing else needs telling, so a command does not know who shows the text.
5. **Frame.** Once no input is waiting, `RenderFrame` scrolls each view to its cursors and draws the views, status bars and message bar into the `screen` grid, laying out only the visible rows and colouring only the visible lines. `ScreenFlush` writes the cells that changed.

Loading runs before the loop: `loader` turns the command line into the list of files, `workspace` holds them as entries, and an entry's file is read into a `document` the first time it is used.

## Terminal

Startup (`TermStart`):

1. Check that standard input and output are a terminal, save the terminal mode, install signal handlers and register `TermStop` as the `Fatal` cleanup.
2. Enter raw mode with `cfmakeraw`.
3. Handshake: send the keyboard protocol query (`CSI ? u`) followed by a cursor position request (`CSI 6 n`). Every terminal answers the second, so a cursor report with no keyboard report before it means the kitty keyboard protocol is missing, and the editor exits with an error. No answer within a second is also an error. This happens before the alternate screen is entered, so a failure leaves nothing on screen.
4. Enter the alternate screen, push keyboard protocol flags (disambiguate only), enable bracketed paste and set the cursor shape.

`TermStop` undoes these in reverse order. The keyboard protocol keeps a separate flag stack per screen, so the flags are popped before leaving the alternate screen. `TermStop` only uses `write` and `tcsetattr`, so it is safe in a signal handler. It runs on normal exit, through `Fatal`, and from handlers for SIGTERM, SIGHUP, SIGINT, SIGQUIT, SIGSEGV, SIGBUS, SIGFPE, SIGILL and SIGABRT. Those handlers then re-raise the signal with its default action.

SIGWINCH writes a byte to a self-pipe. The main loop `poll`s standard input and the pipe, so a resize wakes it like input does.

### Input

With only the disambiguate flag, plain text (including shifted characters) still arrives as UTF-8, and unmodified Enter, Tab and Backspace still send their legacy bytes. Every key with Ctrl or Alt, and Escape, arrives as `CSI code ; modifiers u`. Terminals still use the legacy forms for some keys under the protocol (`CSI 1;5A`, `CSI 5~`, `CSI H`), so the decoder accepts both. Key codes are always the unshifted key, so Ctrl-Shift-S is `{'s', ctrl|shift}`. Lock modifiers are ignored.

Escape is a sequence under the protocol, so a lone escape byte only appears when a sequence is split across reads. The main loop waits up to 50 ms for the rest, then treats it as the Escape key. A bracketed paste is one event however many reads it spans, and its text is passed on unchanged.

### Screen

Each frame clears the back grid, draws everything, and `ScreenFlush` compares it with the previous frame. A cell holds a whole grapheme cluster (its bytes live in a per-frame text buffer) and a style. A wide character uses two cells, the second with width 0. After writing any non-ASCII cell the writer moves the cursor explicitly before the next cell, so a terminal that disagrees about a character's width cannot shift the rest of the row. A resize clears the terminal and redraws everything.

## Text

### Buffer

A buffer is a flat array of lines. Each line is a `StrBuf` holding its bytes without the line break, so joining the lines with `\n` gives the text. There is always at least one line: an empty buffer is one empty line, and text ending in `\n` has a final empty line. A `Position` is a line index plus a byte offset in that line. Display columns are always derived from the bytes, never stored.

Every change is `BufferReplace(range, text)`: insertion is an empty range, deletion is empty text. After each replace the buffer calls its listeners with a `BufferChange` (start, old end, new end, old text, new text). Cursors, views, highlighting and undo all follow edits through listeners, so there is one place where text changes. Undo and redo are inverse replaces. A listener must not change the buffer while it is being notified. Edits inside one line take a fast path that touches only that line. `BufferSetText` replaces everything without notifying, for loading. Every replace, `BufferSetText` and `BufferSwapText` (a reload) adds one to the buffer's `revision`, so something worked out from the text (the expansions Alt-Left returns through) can tell it is out of date without listening.

### Text and Unicode

Bytes are stored exactly as read. An invalid byte is treated as one U+FFFD code point wherever text is decoded, so invalid UTF-8 survives editing and saving untouched. Cursor movement steps over grapheme clusters, using the extended grapheme cluster rules except the Indic conjunct rule (GB9c), which would need another table. `Utf8PreviousBoundary` works backwards from the cursor with only the context it needs (a run of regional indicators, or an emoji ZWJ sequence), so moving left on a very long line stays cheap. A cluster is as wide as its first code point, except that a regional indicator pair (a flag) and a pictographic character followed by U+FE0F are two columns.

### Files

`FileRead` reads a file whole as it is on disk, and `FileLoad` reads through it, so both refuse the same files: `FileRead` refuses anything that is not a regular file, files over `maxFileSize` (100 MB) and files with a nul byte in the first `binaryProbeSize` (4 KB) bytes. A missing file is not an error (`FileStatusNew`): `FileLoad` gives an empty buffer that the first save creates. The file is opened with `O_NONBLOCK` so a named pipe is refused instead of hanging. Line endings are normalised in one pass: every `\r\n` becomes `\n`, and the more common of the two endings (LF on a tie) is recorded and written back on save. A file with both endings is normalised to the more common one, with a message. A `\r` that is not before `\n` is ordinary content (shown as `^M`). So a file that uses one ending consistently round trips byte for byte.

`FileSave` writes to a temporary file (`.<name>.editor-XXXXXX`) in the target's folder, sets its permissions, `fsync`s it and renames it over the target. Symbolic links are resolved first, so the link stays and its final target is replaced. A broken link is refused, because the rename would replace the link with a regular file. The permissions of an existing file are kept, and a new file gets `0666` less the umask. Ownership is not copied, and a hard linked file loses its link, because the rename gives it a new inode.

Each `File` keeps a `FileStamp` (device, inode, size, modification time) from its last load or save. Before writing, the target is checked against it. If the file changed on disk, or appeared where there was none, the save returns `FileStatusChanged` and is only done when the caller asks again with `overwriteChanged`. A file deleted since loading is simply written again. The same comparison, `FileChangedOnDisk`, runs when switching to an entry that was already open, which notes "changed on disk (alt+r reloads)" in the message bar. An existing file without write permission is refused, even though the rename would succeed, because the folder is writable.

## Views

### Layout

`layout` is the only place that turns bytes into columns. `LayoutNext` walks a line one grapheme cluster at a time and gives each cluster its display column (from the line start) and width. Printable ASCII followed by ASCII takes a fast path that skips the grapheme rules. A tab is as wide as the distance to the next multiple of `tabWidth`, measured from the start of the logical line even when the line is wrapped. An ASCII control character is drawn as `^X` in two columns. An invalid byte, a C1 control character, or a cluster with no width of its own (such as a lone U+200B) is drawn as U+FFFD in one column, so nothing on a line is invisible.

Measuring a column, finding the byte at a column, and starting to draw part way along a line all start from the line's beginning, since columns depend on everything before them. `LayoutBeginAt` and `LayoutBeginAtColumn` pass over runs of printable ASCII a byte at a time without reading clusters (a byte followed by a non-ASCII byte is left to the full rules, since a combining mark could join it), so on a 17 MB line a column takes about 5 ms instead of 35.

`LayoutWrap` splits a line into visual rows. A row breaks after its last space or tab that fits, or else just before the cluster that does not fit. Wrapped rows have no continuation indent. Rows hold at most one column less than the text width, so the end of the line always has a cell on its last row for the cursor, and a line that ends exactly at the edge never shows an empty row after it. Only a cluster too wide for a row of its own (a wide character in a one or two column view) can fill the last row, and then an empty row follows it. Without soft wrap a line is one row.

### Visual rows

A `ViewRow` is a line plus the index of one of its rows. `ViewStep` moves forward or back by any number of visual rows and stops at the ends of the buffer. Vertical movement, paging, scrolling and the scroll margin are all written against `ViewStep`, so the same code serves wrapped and unwrapped views. Nothing holds a row index for the whole buffer. A wrapped line is laid out when it is reached, so the cost depends on the rows stepped over, not the buffer size. Without soft wrap every line is one row, and stepping is plain arithmetic on line numbers, so a jump across a million lines is instant. A wrapped line of 4 KB or more keeps its rows in a small cache in the view (four lines, emptied by any change to the buffer), because scrolling and drawing ask for the same line's rows many times a frame.

Each cursor keeps a desired column: its column within its visual row. Up, Down, PageUp and PageDown aim for it, and every other movement resets it. Home and End act on the logical line. Up on the first row goes to the start of the buffer, and Down on the last row to the end.

### Scrolling

The view keeps its first visible row (`top`) and, without soft wrap, its first visible column (`leftColumn`). `ViewScrollToCursor` runs before every frame, so movement, resizing and toggles all end with the cursors in sight. It keeps `scrollOffset` rows between the cursor and the top and bottom edges (capped at just under half the height). With several cursors whose heads span fewer rows than the view, it keeps the whole span in sight instead, with the margins when they fit and without them when they do not, so adding cursors does not scroll the first ones away. A span taller than the view falls back to the primary cursor. The margin shrinks to the rows that exist before or after the cursor, which is how it yields at the start and end of the buffer. The view never scrolls so far that empty rows show below the end of the buffer. Columns get the same margin, and it yields at the start of the line.

Alt-Up and Alt-Down move `top` by one row and leave the cursor alone. They refuse (with a message) when a cursor being kept in sight would end up inside the margin, or the view would pass either end. PageUp and PageDown move both the cursor and `top` by the height less one row, so the cursor keeps its screen row.

### Rendering

`RenderFrame` gives the view every row except the bottom two (the status bar and the message bar), scrolls it to its cursor and draws it. With a split it draws two panes, left to right, either side of a one column separator, each with its own status bar. The gutter is the line number right aligned with a space either side, at least three digits wide. Only the first row of a wrapped line is numbered. With whitespace display on, a space is drawn as `·` and a tab as `→` in its first cell, in the `whitespace` colour. The ruler is drawn as `│` in the cell just after `rulerColumn` before the text, so text covers it, and spaces and tabs let it show through. A cluster cut by the left or right edge of the text area shows as blank cells. Drawing a line starts at its first visible row, or without soft wrap at the cluster under the first visible column, so the part of a long line before the view is never laid out cluster by cluster.

With more than one cursor, the terminal cursor is hidden and every cursor (the primary one too) is drawn by switching its cell to the `cursor` style (reverse video on the default colours) after the text is drawn, so it reads as a block whatever the cell held. A cursor at the end of a line covers the empty cell after it. Cursors outside the view are skipped by their line number before anything is measured.

A selection is drawn with the `selection` background behind the text's own colours. When a selection continues onto the next line, one selected cell after the end of the line shows that the line break is included.

The status bar shows the name (shortened in the middle to fit) with `[+]` and `[RO]` on the left, and the cursor count (with more than one), the wrap state, file type, line ending, `line:column`, line count and `open:loaded` buffer counts on the right. When the window is too narrow it keeps only `line:column`, and then nothing, on the right. Below `minWindowWidth` by `minWindowHeight` the editor shows only "terminal too small".

## Editing

### Cursors follow changes

A view listens to its buffer. After every `BufferReplace` it moves each cursor with `BufferAdjust`: a position before the change stays, one inside the replaced text moves to its start, and one at or after its end moves with the text that follows. The view's first visible line shifts the same way. So a command edits at one cursor and the others stay on their text without the command knowing about them. The other view of a split follows the same way.

An edit command loops over the cursors, replaces each one's range, and puts that cursor after its new text. When the loop ends, cursors that now overlap are merged and every desired column is reset. Commands that rewrite lines replace only the bytes that change, so every view of the buffer, not just the one editing, keeps its cursors on the same text: indent and dedent make one replace per changed line, Ctrl-D inserts the copy above the lines, moving lines takes the neighbouring line out and puts it back on the other side (so the moved lines are never replaced; cursors on the neighbour in another view move to the end of the moved lines), each join replaces only a line break and the blanks after it, and trimming replaces only each line's trailing blanks (Ctrl-T on the lines the cursors touch, through the same line editing as indent, and Ctrl-Shift-T on every line). Sorting is the exception: it replaces the whole block of lines at once, so another view's cursors inside it move to its start. A sort orders line indexes with a stable merge sort (insertion sort for short runs) and builds the new text once; the case folded orders skip the common prefix of two lines up to its last ASCII byte (which always ends a code point) before folding, which roughly halves their time. Sorting by length measures each line's display width (`LayoutColumn`) once into an array before sorting, compares widths first and breaks ties in ascending text order; descending reverses only the comparison of the key (widths, or text), so equal lines keep their places. 1M lines sort in about 0.5 s by bytes, 0.75 s ignoring case and 0.75 s by length. Case conversion needs a selection (without one it says so and changes nothing) and converts each selection code point by code point and replaces only the span from the first code point of a line that changes to the last one, working from the last selection back so the offsets still to convert stay put. A mapping can change a character's byte length (`Ⱥ` is two bytes, `ⱥ` three), so the editing view's cursor ends are remembered as a line and a code point number before the edit and turned back into bytes after it; simple mappings are one to one, so the count of code points never changes. 1M lines convert in about 0.4 s. Indent and dedent then put the editing view's cursors back themselves, so a cursor at the start of a line stays before the new indentation. Ctrl-D, Ctrl-K, Ctrl-Up/Down, Alt-J and Alt-O first collapse to the primary cursor, and so do the commands that place one cursor (Ctrl-L, Ctrl-M, Alt-M and the search commands).

### Multiple cursors

The primary cursor is the one most recently added. Esc collapses to it, the status bar reports its position, and the view follows it when the cursors do not all fit. Movement merges cursors that meet, as edits do. Merging finds it again by value after sorting, so it survives the cursors around it being joined.

Ctrl-E with no selection at the primary cursor selects the word at every cursor that sits on or just after one. With a selection, it finds the next occurrence of the primary selection. When the selection is exactly one of the matches the document highlights (`SearchMarks`: the last search's matches, regular expressions included, or unknown words), the occurrences are those matches, found with the document's own match set. Otherwise the selection must be on one line, and its text is escaped into a case matching pattern (whole word when the selection is exactly one word). Either way the search runs forward from the selection's end with `MatchFind`. Matches that overlap any cursor are passed over, and the search stops once it has gone round the end and come back to the primary selection, so pressing it again after the last occurrence reports "no other occurrence" instead of looping.

Alt-E finds the next occurrence the same way, passing over the primary cursor's own selection, and moves the primary cursor there instead of adding one, which leaves the occurrence it held unselected. Ctrl-Shift-E adds a cursor at every occurrence and keeps the primary cursor, so the view stays where it is. It merges the cursors once, then walks the buffer's matches and the sorted cursors together, so a match a cursor overlaps is passed over in one pass, and merges once more at the end; merging after each match would sort the set once per cursor. Both first select the word at the cursor when there is no selection. Ctrl-Alt-Up and Ctrl-Alt-Down step one visual row from the first or last cursor (from the outer end of its selection, so the new cursor never lands inside it) and keep its desired column, so a column of cursors goes down a ragged block of lines at one column.

A paste with as many lines as there are cursors (not counting the empty line after the last line break of a line wise copy) gives the cursors one line each, in buffer order. Otherwise each cursor gets the whole text.

The cost of an edit grows with the square of the cursor count, because each cursor's replace adjusts every other cursor. With 10,000 cursors, typing a character takes about 0.2 seconds.

Enter copies the indentation before the cursor and adds one level after `{`, `[` or `(`. With the matching closer right after the cursor it puts the closer on its own line below. Blanks after the cursor are dropped, and a line that holds only blanks before the cursor is left empty rather than with trailing blanks. One level is `tabWidth` spaces, or a tab when expand tab is off (Alt-T).

### Undo

`undo` listens to the buffer too, and records each change as `{start, oldText, newText}`. Everything between `UndoBegin` and `UndoEnd` (which nest) is one group, which also keeps copies of the cursor set from before and after. Undo replays a group's records backwards as inverse replaces and restores the "before" cursors; redo replays them forwards and restores the "after" cursors. A change outside a group is a programming error and ends the editor through `Fatal`, so nothing can slip past the history.

A typing, backspace or delete edit joins the last group when it is of the same kind, nothing has been undone, and nothing broke the run. `app` calls `UndoBreak` before every command except backspace and delete, and before a paste. Within a group, a change that simply continues the last record (typing after it, backspacing before it, deleting at the same place) extends that record, so typing a line costs one record.

The history keeps a save point: the number of applied groups when the text matched the file. The buffer is modified when the history is not at its save point, or its line ending differs from the one on disk, so undoing back to the saved text, or switching the line ending back, clears `[+]`. Starting a new group after an undo drops the groups that could have been redone, and the save point with them when it was among them. A reload clears the history. There is no depth limit.

### Prompts

The message bar doubles as the prompt. `PromptAsk` edits one line of text (Left, Right, Home, End, Backspace, Ctrl-Backspace, Delete, paste up to the first line break), and `PromptChoose` waits for one of a few letters (a capital letter counts as its lowercase choice, unless it is a choice of its own, as the capitals are for sort). Escape cancels either. The answer goes to a callback, and the prompt is closed before the callback runs, so a callback can open the next prompt. `PromptHandle` adds two optional handlers to a text prompt: one told about every change to the text (the picker filters with it), and one asked to complete the text on Tab (Ctrl-O uses it).

### Learning mode

Learning mode takes every key while it is on, ahead of pickers and prompts, so no command runs, and pastes are dropped. It uses the message bar, which `app` clears before each key, writing the result of the last key and the next question each time. The bindings held with Ctrl or Alt (except its own) are shuffled with `arc4random_uniform` and asked in turn, and shuffled again once all have been asked. A key is right when it is the binding's key (`KeyEqual`); a wrong one is named with what it does (`KeymapFind`), and after three misses the answer is given, after which pressing it no longer counts as right. Esc, which has no modifier and so is never asked, ends it.

### Save flow

`save` runs a queue of documents: the current one for Ctrl-S, every modified one for Ctrl-Shift-S and for "save all" when quitting or replacing the buffers. Each document is trimmed (when `trimTrailingWhitespace` is set), then written, and the next one starts from the completion of the last. A document without a name asks for one first, and during save all it is made current so the user can see what they are naming. A name that exists asks "overwrite?", and `FileStatusChanged` asks "changed on disk; overwrite?". Any error, refusal or cancel stops the queue, and the callback waiting for the end of the run (quit, replace) never runs. A save that fails after save as leaves the buffer unnamed again.

The Alt-X file menu remembers the current entry's serial, then asks for the choice and the path, so its answers never act on another buffer. Rename goes through `DocumentRename` and `FileRename`: `rename(2)`, or on `EXDEV` a copy into a temporary file next to the target (with the original's permissions, then renamed over it) followed by removing the original. The path changes as for save as, including the language, and the entry's file id is refreshed (`WorkspaceRenamed`) so Ctrl-O finds it under the new name. The stamp moves to the new file only when the old one matched it, so changes made by another program are still caught by the next save. A document whose file was never created only changes its path. Save a copy calls `FileSave` with a temporary `File` (the target path, the document's line ending, no stamp) and `overwriteChanged` once an existing target was confirmed, so the document's path, stamp and save point are untouched and nothing is trimmed. A target that is the document's own file (by device and inode) is refused. Delete unlinks the file (a missing one is fine) and removes the entry.

### Clipboard

Copy sends the text to `wl-copy` on standard input, and paste reads `wl-paste --no-newline --type text`. Both run with `posix_spawnp`, standard error to `/dev/null`, and a two second limit, after which the command is killed. The editor ignores SIGPIPE so a command that exits early cannot end it, and resets SIGPIPE to the default for the command. Without `WAYLAND_DISPLAY`, or when the command fails, the in-process copy is used.

Copy with no selection is line wise: each cursor's line, ending in `\n`. The clipboard remembers the last copy and whether it was line wise. When a paste finds exactly that text, it is inserted as whole lines above the cursor's line instead of at the cursor.

A paste, from Ctrl-V or a bracketed terminal paste, has `\r\n` turned into `\n` (a lone `\r` stays, as when loading) and is one undo step without any auto indentation.

### Saving and reloading

`document` keeps the file's line ending from its last load or save. Saving runs trailing whitespace trimming first when `trimTrailingWhitespace` is set (one undo step, so the screen matches the file), then `FileSave`, then marks the save point. Reload reads the file into a separate buffer and swaps the text in only when that worked, then clamps the view's cursors and scroll position into the new text.

### Split view

Each document has two views, one per slot, and each side of the split uses its own slot of every document. The focused side's entry is the workspace's current entry, so every command works on the focused view without knowing about the split. The workspace also keeps the entry the other side shows and which slot is on the left, so Ctrl-I only flips that, and Ctrl-J swaps the current and other entries along with the focused slot. Ctrl-Alt-Right and Ctrl-B put the new view in the other slot, on the right.

A document's `view` points to the view of the slot that last had focus on it, which is the one commands use. When a side shows a document whose `view` is the other slot's, it first copies that view's cursors and scroll position into its own, so a buffer opens where it was last seen rather than where this side last left it. A side that switches back to a buffer it was the last to use keeps its own position. Both views stay buffer listeners for the document's lifetime, so an edit through either one moves the other's cursors and scroll position as well. Undo restores the cursors only in the view that undoes.

Below `minSplitWidth` (80) columns only the focused view is drawn, at full width, and nothing about the split changes, so widening the window brings both back. Only the focused view shows its cursors, and pickers and prompts span the whole window. Replacing the buffers with a folder resets the workspace, which ends the split.

## Search

### Patterns

One pattern syntax serves Ctrl-F, Ctrl-R, Alt-N, Alt-P and project search. A pattern is literal text, or a regular expression (below) when its options say so. A `^` at its start and a `$` at its end are anchors, and the escapes `\t`, `\r`, `\n`, `\\`, `\^` and `\$` stand for those characters; any other backslash is literal. A match never crosses a line break, so a pattern holding `\n` never matches, and an empty pattern matches nothing, so matches are never empty and stepping through them always moves.

Without case matching (the default, toggled with Ctrl-I for the session), the pattern is kept as case folded code points, and the text is folded one code point at a time as it is compared, with a fast path for ASCII. Folding can change a character's length (the Kelvin sign folds to `k`), so offsets are always those of the original text. A match must start and end on grapheme cluster boundaries, so `e` does not match the start of an `e` with a combining accent. Ctrl-W builds a whole word, case matching pattern from the word at the cursor (word characters as for word movement).

### Regular expressions

Ctrl-R in a search prompt sets `regex` in the pattern options for the session, as Ctrl-T does for case. Every matcher already goes through `PatternFind` and `PatternReplaceLine` (`match`, `render`, `preview`, `project`, `search`), so highlighting, Alt-N and Alt-P, replace and project search and replace take regular expressions with no code of their own. Ctrl-W and Ctrl-E build literal options. The engine is the editor's own (`regex`), not libc's `regcomp`, which works on bytes in the C locale the editor runs in: `.` would match one byte, case would only fold in ASCII and `\w` would disagree with `Utf8IsWord`. It also has to search a slice of a line that is not nul terminated, and stay linear on long lines.

`RegexCompile` parses the pattern by recursive descent straight into instructions: consume a code point (a literal, any, or a class of sorted ranges), split, jump, save a group boundary, assert (line start or end, word boundary or not) and match. Jumps are relative to the instruction, so a block of code can be moved (a repetition inserts its split in front of the atom) or copied (`{m,n}` repeats the atom's code, the optional copies nested so that skipping one skips the rest, as a counted loop does). Programs are capped at 4096 instructions. Without case matching, literals are stored folded and compared with the folded text, and a class tests a code point, its upper and lower case and its folding, so `[A-Z]` matches `a`. `\w` and `\b` use `Utf8IsWord`, the same words as whole-word search.

`RegexFind` is a Pike VM: a Thompson NFA simulation whose threads stay in priority order, so it finds the leftmost match and, among those, the one Perl's backtracking would, in time proportional to the line's length times the program's size. Each step decodes one code point, and the threads that consume it are followed through splits, jumps, saves and asserts (with a mark per instruction, so no instruction is added twice in a step and empty loops end) into the next list. A new thread starts at each position, with the lowest priority, until something matches; a match cuts off the threads after it, and the ones before it run on in case they match later. A match must be non-empty, so the VM ignores a match instruction reached at the position its thread started, which also makes `a*?` take one `a` rather than none. When every match starts with one ASCII byte, the search skips to it with `memchr` while no thread is alive (not without case matching for `k` and `s`, which the Kelvin sign and long s fold to), and a pattern starting with `^` runs at offset 0 only. Scratch space lives in `regex` and grows to the largest program, as the editor searches from one thread.

Finding only needs where a match starts and ends, so threads carry two slots. A replacement that names a group (`\1` to `\9`, expanded by `PatternExpand`) runs the VM again, anchored at the match's start with all ten groups, which gives the same match. `PatternFind` still applies the grapheme cluster check to a regex match, and searches again from the next code point when it fails. Group positions follow the VM's semantics, which differ from Perl's in one corner: a repetition whose body can match empty ends there in Perl (`(\B|.)*` on `ab` takes only `a`), while the VM goes on with the other alternatives (and takes `ab`), as RE2 does. A random comparison with Python's `re` (patterns over a small alphabet, ASCII text) agrees on every whole match outside that corner.

A search of 1,000,000 lines that matches nothing takes about 0.13 seconds when the pattern starts with a literal byte (the same as a literal search) and about 0.6 seconds when it does not (`\d{3}`). Replacing 350,000 matches of `(\w+)_(\w+)` with `\2_\1` takes about 1 second, and a regex search of 100,000 small files about 0.2 seconds from the page cache.

### Match sets

Matches are never stored. Each document has a `marks` kind (none, search or spell), and the last search pattern is shared by every document. Rendering finds the matches on each visible line as it draws it, and Alt-N and Alt-P scan from the cursor, line by line, going round the end of the buffer once. So an edit can never leave a highlight or a step out of date, and the cost is proportional to the lines drawn or scanned. A match that is also selected is drawn in a stronger colour, which is how the current match stands out. Esc clears multiple cursors first, then the selection, then the highlights.

Incremental find saves the cursors, scroll position, marks kind and last pattern when it starts, and puts all of them back on Esc. Each change to the prompt searches again from where it started, so deleting a character goes back to an earlier match. The search prompts take Up, Down, Ctrl-N, Ctrl-P, Ctrl-T and Ctrl-R before the prompt itself sees them; the replacement prompts leave Ctrl-I and Ctrl-R alone.

### Replace

Ctrl-R runs from the start of the selection to the end of the buffer, then from the top back to where it started. That stop position moves with each replacement through `BufferAdjust`, and every search continues after the last replacement, so replacing `a` with `aa` cannot loop. The run is one undo group, opened before the first replacement and closed when the run ends (answers come one prompt at a time, but the prompt takes every key, so nothing else can edit in between). Replacing all rebuilds each line once (`PatternReplaceLine`, which project replace shares) and replaces it with a single change, so 100,000 matches take about 0.1 seconds.

### Spell check

The word list is `words.txt` in the config folder. It is loaded into a `Buffer`, one word a line, by `FileLoad` the first time Alt-C or Alt-Shift-C needs it, and again when its stamp shows another program changed it (`FileChangedOnDisk`, checked by those commands only, not as lines are drawn). Lines out of byte order (a list edited by hand) are sorted in memory, and the list is binary searched in byte order, leaving out the empty line after a final line break. Without the file, spell check says where to put one and finds nothing. Alt-Shift-C takes the word at the cursor as the spell check reads words (so the word Alt-C selected, with the cursor at its end, is the one asked about), and finds the entry that makes it known: as written, or its lowercase form for a capitalised word. Adding inserts a line where the search ends and removing deletes one (both through `BufferReplace`, with no listeners), and the list is saved with `FileSave`, so it is written atomically, through a symbolic link, keeping its permissions; when the save fails, the change is undone in memory. Unknown words are found again as each frame is drawn, so the highlights follow the list at once. A run of letters, digits, `_` and apostrophes is read whole: runs with digits or `_` are skipped, apostrophes at either end are trimmed, words in capitals only are taken for acronyms, and words inside a blank separated chunk holding `://`, `www.` or `@` are skipped as links. A word is known when it is in the list as written, or when it starts with a capital and its lowercase form is. Typographic apostrophes are looked up as `'`. Letters are those of the Latin, Greek and Cyrillic scripts; other scripts are not checked. In a highlighted buffer, the spell match set asks `HighlightSpellable` about each unknown word's first byte and passes over the ones outside the text it checks (see Highlighting). Other buffers are checked in full.

### Scans

Project search and the symbol index both go through many loaded entries without opening them, so `scan` does that walk once for both. A client gives it the entry indexes and four functions: `wants` (optional) decides from a file's current stamp whether to read an entry that is not open, `visit` takes one entry (its open document, or the text `FileRead` gave, with its stamp) and may end the scan, `progress` writes the message, and `finish` hears how it ended (done, skipped and whether Esc stopped it). `ScanContinue` visits entries for about 20 ms, then returns so the loop can draw the progress and read keys (it polls with no timeout while a scan runs). While a scan runs, `app` hands every key to `ScanKey`, which ignores all but Esc, and drops pastes, so no entry is added or removed and the indexes stay valid. One text buffer is reused for every file read, and freed when the scan ends. The scan is over before `finish` runs, so a client may start another from it.

### Project search

Alt-Shift-F takes its pattern through the search prompt (so Ctrl-I and recall work as in Ctrl-F), and the pattern becomes the last search. The scope prompt then splits its answer at blanks into two `filter` lists, the patterns to pick and the `!` patterns to leave out, and tests each entry's display path (after any leading `./`) against both. An unnamed buffer has no path, so only a scope with nothing to pick takes it. Entries already refused as binary or too large are counted as skipped without being read.

The search never blocks the main loop: it is a scan (see Scans). Open entries are searched from their buffer, the others as `scan` reads them, and scanned line by line with `\r` before a line break left out, so line numbers match what opening the file gives. A case-sensitive search first checks the whole file with `memmem`. A matching line is recorded once, with its first match and up to 200 bytes of its text, and the search stops at `maxProjectHits` lines. Searching 100,000 small files from the page cache takes about half a second. Nothing is opened, so the open count stays the same.

The hit list is a picker with a preview: `PickerShowPreview` gives the picker a function that draws beside the list when the window is at least 80 columns wide. Without a preview the picker shows each item's note, here the line's text. The preview (`preview`, shared with the symbol pickers) reads an unopened file again with `FileRead` (keeping the last one read) and draws a header naming the file and line (shortened in the middle to fit), then the lines around the hit with their numbers, scrolled sideways when the match would be off screen, and every match highlighted. Opening a hit switches to its entry (opening it) and selects the match on the stored line, or the line's start when the text has changed. Each hit also records the revision of the buffer it was found in, or that it was read from disk. Showing the list again (Alt-F) first finds the hits again, with the same line search, in every listed entry that is now open and whose buffer has another revision (or whose hits came from disk), copying the other entries' hits as they are, so an edited line that no longer matches drops out and line numbers follow lines inserted above. Only entries with hits are searched again, so a file that starts to match is found by a new search. Hits stay in entry and then line order, so the list starts after the hit opened last by comparing entry serials and lines, not by index. Hits keep their entry's serial, so closing a buffer or opening a folder never makes one lead to another file: the list leaves out hits whose serial no longer matches and counts them in its title. A folder opened with Ctrl-O still clears the list, only to free it.

### Project replace

Ctrl-R in the hit list replaces on the lines the list shows, so the filter decides which lines take part. The picker hands keys with modifiers to a handler the list gives it (`PickerHandleKeys`) before its filter prompt sees them, and tells which items the filter shows. The handler copies their ids, then `PickerSuspend` closes the list while keeping its items, filter and selection, and `search` asks for the replacement with the same prompt and recall as Ctrl-R. After "replace in N lines of M files? (y/n)", Esc at either question or `n` brings the list back as it was (`PickerResume`).

Hits come grouped by entry, so the chosen ones are taken an entry at a time. Each entry is opened (one that has been closed or cannot be opened is counted and reported), and its lines are replaced from the last up, so a replacement holding a line break leaves the lines still to come where the hits say. Each line is matched again in the document's current text, so a line edited since the search takes only the matches it still has, or none. The line is rebuilt with `PatternReplaceLine`, which finds every match in the original text, so replacing `a` with `aa` ends, and each entry's changes are one undo group. Nothing is saved: the message points to Ctrl-U to review the changed buffers and Ctrl-Shift-S to save them. The hits no longer describe the text, so the list is cleared. 10,000 lines in 10 files take about 0.07 seconds.

## Buffers

### Loading

`loader` turns paths into a `LoaderList` of display paths and file ids (device and inode). A path that does not exist is a new file, unless it ends in `/`, which is an error. A folder is walked depth first with `openat` and `fdopendir`, and each listing is sorted by name. Entry types come from `d_type`, so a regular file costs no `stat`: its id is the folder's device and the entry's inode. A link is followed with `fstatat` and kept only when it leads to a regular file, so links to folders are skipped (and folders are opened with `O_NOFOLLOW` to be sure). Other kinds (pipes, sockets, devices, broken links) and `.git` folders are skipped. A folder that cannot be read is counted and reported in the message bar.

Files are de-duplicated by id in a hash set, so a file named twice, inside a named folder, or reached through a link appears once, under the first path that reached it. New files are de-duplicated by path. The walk stops as soon as it would pass the limit. At startup that ends the program with a message before the terminal changes; at runtime the operation is refused. Nothing but folder listings and `.editor` files is read, so a 100,000 file tree loads in well under a second.

### .editor files

Each folder in a walk is probed for `.editor`. When there is one, its patterns replace the ones from above for that folder and everything below, and paths are matched relative to it. Patterns come one per line; `#` at the start of a line or after a blank starts a comment. `filter` knows four forms: a name (`foo.txt`, `*.c`), a folder name (`bar/`), and either one tied to a path when it starts with `/` or has a `/` inside (`/foo/foo.txt`, `/*.c`, `/bar/`). `*` matches within one name and is the only wildcard. A folder is tested before it is entered, so a matched folder is never read, and a file also matches a folder pattern that matches any folder above it (which project search scopes rely on, so `src/` picks everything under any `src` folder). The folder that holds an `.editor` file is judged by the patterns above it, not its own. Files named on the command line are always loaded, and `.editor` files are only read when loading (startup and Ctrl-O on a folder).

### The buffer list

`workspace` holds one entry per loaded file or unnamed buffer: the path (until opened), the file id, the document once opened, a refusal reason, a number for unnamed buffers, and a "last used" tick. The document is allocated when the entry is first used, and its path moves into the document. A file over the size limit or with a nul byte in its first 4 KB is refused, remembered as such and never read again, and the current buffer stays. Other errors (permissions) are tried again next time. The status bar's `open:loaded` counts open documents and entries.

Each entry also gets a serial from a counter that is never reset, not even when a folder replaces every entry. Entries are only appended, and `WorkspaceRemove` compacts the array without reordering it, so serials stay sorted and `WorkspaceEntryOf` finds an entry by binary search. Anything outside the workspace that remembers an entry (project hits, the file menu, a close waiting for its save) keeps the serial, so a removed entry simply stops matching and nothing has to be fixed up. `WorkspaceRemove` fixes only the workspace's own state: `current`, `other` and `openCount`. When the current entry goes, the most recently used one takes its place (or the first that opens, or a new unnamed buffer when none is left). When the other side of a split showed it, that side shows its most recently used entry other than the current one (or the current one), starting where that entry was last seen.

Alt-Q closes the current buffer through `WorkspaceRemove`. With unsaved changes it first asks "save changes? (y/n/c)"; `y` runs the ordinary save queue with the close as its completion, so a cancelled or failed save leaves the buffer open.

Each document owns its views (one per side of a split), which keep their cursors and scroll position while another buffer is shown, and keep following edits because they stay buffer listeners. App never keeps a document or view pointer across commands, since opening a folder frees every document.

At startup with several paths or any folder, the first entry that opens is made current and the buffer picker opens over it, so Escape leaves you in it. With none openable, or none at all, an unnamed buffer is used. Ctrl-O on a file adds it (or finds it among the loaded entries) and switches to it. On a folder it first loads the new list, refusing an empty or oversized one, then asks about unsaved changes, then frees everything and loads the new list as at startup. The session remembers which paths were folders (from the command line, or the Ctrl-O folder once it replaced everything) and every path their walk found. Alt-Shift-R walks those folders again, skipping any that are gone (a missing path would otherwise be listed as a new file), and appends each file whose path was not found before and that no entry already is, by file id or by path (a save replaces the file, so its id changes). The walk then becomes the known list, so a closed buffer is not added back, and a file left out because the workspace is full is offered again next time.

Ctrl-PgUp and Ctrl-PgDn step through open entries in load order, wrapping. Ctrl-Tab goes to the most recently used entry other than the current one. The buffer pickers list entries most recently used first, then named ones by path, then unnamed ones, with a note for a refusal. A mark before each name shows its state: `+` for unsaved changes (only an open entry can have them), `·` for any other open entry, and nothing for one only loaded. Both are faint, and one column wide, so names stay aligned.

### Pickers

`picker` takes a list of items (text, an optional note, an id) and shows it over every row above the message bar, with a bar naming the list and counting matches. The filter is a text prompt with a change handler, so it edits like any prompt. Up, Down, PageUp, PageDown, Home and End are taken by the picker first, and Enter with no matches does nothing. A list may also take keys with modifiers (the project list takes Ctrl-R), and may be suspended while a question is asked and resumed as it was. An item may be marked (`PickerMark`): a list with a marked item draws a marker column before every item, outside the text, so filtering and shortening never see it. Each item keeps a case folded copy of its text, so filtering 100,000 paths is a byte search per item. A filter matches anywhere in the item, `^` at its start ties it to the start and `$` at its end to the end, and both ignore case. Long items are shortened in the middle. The Ctrl-H list is built from the binding table, sorted by description, and Enter runs the picked command.

### Jump history

A jump is a command that sends the cursor somewhere it could not reach with a few keys: Ctrl-L, Ctrl-Home and Ctrl-End (not their Shift forms), opening a project search match, picking a symbol with Alt-S or Alt-Shift-S, Ctrl-] and Ctrl-[, and Alt-D. Before it moves, the command calls `JumpRecord`, which stores the current entry's serial and the primary cursor's position. `jump` keeps 32 places, the oldest dropped first, and an index into them, much like undo. Alt-[ from the newest place first stores where the cursor is (so Alt-] can return), then goes to the place before; Alt-] goes to the next. Recording while back in the history drops the places ahead, and the place gone back to is replaced by where the cursor is now. A place equal to the newest is not stored twice.

Places do not listen to edits. A position is clamped when it is used (a line past the end goes to the end of the buffer, a byte past the end of its line to the line end, and a byte inside a code point back to its start). A place whose entry was closed, or that is where the cursor already is, is passed over. Going to a place in another buffer switches to it as Ctrl-P would, so a split's focused side shows it.

## Highlighting

### Languages

Languages are packages: a folder for each in `languages/` of the config folder (`$XDG_CONFIG_HOME/editor`, or `~/.config/editor`), named by its id. README.md describes the files and the directives of a package's `language` file. `LangLoadAll` reads every package's `language` file before the first document opens, in order of id, so a lookup never depends on the order of the file system. It loads no grammar: it records whether the folder holds `parser.so` and `tags.scm`, fills in the defaults (the entry point `tree_sitter_<id>`, with `-` as `_`, and the id as the only injection id), and moves everything into one allocation that lives until the editor exits, so a `const Lang *` held by a document or the symbol index never dangles. Each `Lang` has an `index`, which `highlight` uses for its per-language state. A `language` file with an unknown key, a key given twice, a bad flag value, a line without `=`, extensions without a name or `comment-end` without `comment` leaves its package out, and the first such problem (with a count of the others) is shown in the message bar at startup. Packages are only read from the config folder, never from a project, because a `parser.so` runs with the user's privileges.

`lang` maps a file name to a language: first by the whole name (`files`, such as `PKGBUILD`, matching case), then by extension (ignoring case). A path with neither falls back to the language of its first line, which `document` reads once when the file opens: `#!` naming one of a language's `interpreters`, directly or through `env` (skipping its options and variable settings). The document keeps that answer, so a save keeps the script's language and a rename back to a name without an extension restores it, while a shebang typed into a new file counts only once the file is opened again. A document picks its language when it opens and again after each save or rename, so saving under a new extension changes it, and hands `highlight` the `Lang` itself. The first time a language is used, `highlight` opens its `parser.so` (`dlopen` with `RTLD_NOW | RTLD_LOCAL`, so grammars cannot clash), looks up its entry point, and checks the grammar's ABI against the runtime's range (13 to 15). Handles are never closed, as trees and queries point into the grammar. Then it reads `highlights.scm` (required) and `injections.scm` (optional) with `FileRead` and compiles them, shared by every buffer from then on. A grammar that does not load or a query that does not compile is reported in the message bar once, naming the language and the file, and leaves that language uncoloured; a package without `parser.so` is simply not highlighted. The grammars use only libc, not the tree-sitter runtime, so the editor need not export its symbols. README.md lists the steps for adding a language.

### Parsing

A highlighter listens to its buffer. Each change becomes a `TSInputEdit` applied to the trees at once, and the parse itself waits until a line is asked for, so a burst of edits (many cursors, replace all) costs one reparse. Tree-sitter needs the byte offset of each change, so the highlighter keeps the offsets of line starts, extending them lazily and keeping only those up to the changed line. The parser reads the buffer through a `TSInput` callback, which hands over the rest of the line at the requested point and then its line break, so the text is never copied into one string.

Parsing has a deadline of `maxParseTime` (one second): a parse that runs past it is stopped, and highlighting stays off for that buffer until it is reloaded. Buffers over `maxHighlightSize` (16 MB) are not parsed at all. In both cases the status bar shows the language as "(uncoloured)". A 20,000 line C file parses in about 0.1 seconds, and each keystroke after that reparses in under 2 ms.

### Injections

A grammar with an injection query embeds others: Markdown its inline grammar (for every paragraph and heading), fenced code blocks and HTML blocks; HTML its scripts and styles; inline Markdown its HTML tags. The injected language comes from `#set! injection.language` or from the text of an `@injection.language` capture, and is looked up first by injection id, then as a file extension through `lang`, so a fence can say `js`. Languages without a grammar (regex, jsdoc, phpdoc, comment) are skipped. A PHP heredoc names its language with its delimiter (`<<<SQL`), but its body's text is all named children, which stay with PHP, so it colours as a string. An injected language covers the ranges of its `@injection.content` node, less the node's named children, which belong to the outer language (the `> ` of a quoted code block). Anonymous children are only tokens of the outer grammar, so they stay in. `injection.combined` is not supported: each node is parsed on its own. In PHP, this means each piece of HTML between `<?php ?>` blocks is parsed separately, so a closing tag whose opening tag is in another piece (`</body>` after a block) is an erroneous end tag and loses its tag colour.

Each injection is a layer: a grammar, its ranges and its tree. Layers are found again by grammar and first byte, and follow edits like the main tree, so an unchanged paragraph or code block is not parsed again. An edited layer is parsed incrementally, except for grammars marked `fresh-parse`: Markdown's inline grammar gives different trees when parsed incrementally (found by comparing random edits against fresh parses), and its layers are a paragraph each, so they are parsed from scratch. The grammars added later (Bash, Go, PHP, SQL, XML, YAML, Zig) need no such flag: retyping random lines a key at a time leaves the same trees and colours as a fresh parse. Random edits that leave syntax errors behind can still differ inside those errors, as tree-sitter's error recovery depends on the previous tree; the C grammar does the same, and reloading the file clears it. Layers nest up to four deep. Once there are more than 512, those not used by the last two windows are dropped.

### Colouring lines

`HighlightLine` gives a byte per text byte: the syntax group in the low six bits, plus two flags for spell check. It fills a window of lines (64 before the line asked for and 192 after) by running each layer's highlight query over just those rows. Captures that fail their predicates are dropped. The rest are sorted by start, enclosing nodes before the nodes inside them, and for the same node by pattern, then painted in that order, so an inner node beats the node around it and a later pattern beats an earlier one (the convention of most vendored queries, as in `(identifier) @variable` followed by more specific patterns). Go's query is written for the opposite rule of the tree-sitter command line tool, with specific patterns first and `(field_identifier) @property` after them, so its package sets `first-pattern-wins`, which reverses the pattern order for captures of the same node. Under that rule its `len` and `println` calls colour as functions, because the plain call pattern comes before the builtin one. Injected layers are painted after the layer that holds them. Two windows are kept, one for each side of a split, and any edit invalidates both.

A line over 16 KB (minified code) is coloured only around the part being drawn: from 16 KB before the first byte drawn to 64 KB after it. The window runs the queries once for each run of ordinary lines and once for each long line's span, and clips every capture to the part it was run for, so a node reaching into another part cannot paint over it. Other long lines in the window are coloured around the same byte offset, which suits an unwrapped view scrolled sideways. Asking for a long line outside its span fills the window again. So a keystroke on a 1 MB minified line costs about 30 ms rather than 300. Rendering asks for the groups of each line it draws and starts from that group's style, with selections and matches drawn over it.

A capture name picks the group that shares its first component (`string.special` is `string`), except that any `*.builtin` is `builtin`, and Markdown's `text.*` captures use their second component: `title`, `literal`, `emphasis`, `strong`, `uri` and `reference`, which are markup groups in the theme. A few first components that some queries use for things the theme already colours are aliases: `boolean` is `constant`, `character` is `string`, `conditional` and `storageclass` are `keyword`, `float` is `number` and `module` is `namespace`. The captures left uncoloured on purpose are containers (`embedded`), markers (`spell`, `error`), XML's text and CDATA (`markup.*`), and SQL's column and parameter names (`field`, `parameter`), which would colour most of a query. A capture with no group colours nothing, and `@none` (which Markdown puts on code block contents) clears the colour.

Tree-sitter leaves text predicates to its user. `query` evaluates `#eq?`, `#match?` and `#any-of?` (and `#not-` forms) against the captured text. `#match?` uses POSIX extended regular expressions, with `\d`, `\w` and `\s` rewritten as bracket expressions first, since the queries are written for Rust's regular expressions. `#lua-match?` (Zig) takes a Lua pattern, rewritten as a POSIX one: `%a` style classes become bracket expressions, `%` escapes a character, the lazy `-` becomes `*` (a test only asks whether it matches), and `{`, `}`, `|` and `\` are escaped. An ignored predicate would let its pattern match every node, so Zig would colour every identifier as a constant. The SQL query writes Lua classes inside `#match?` (`"^[-+]?%d+$"`), which match a literal `%d`, so SQL numbers fall through to the string colour of literals. Other predicates (`#is-not? local`, `#offset!`) are ignored.

### Symbols

A package may hold a tags query, `tags.scm` (for the default packages, kept in `languages/<id>/tags.scm`). These are the editor's own rather than upstream's: upstream's C query captures the `function_declarator`, which leaves out the return type, and the contract below needs whole declarations. The query compiles the first time a buffer's symbols are asked for, separately from the highlight query. C, JavaScript, Go, PHP, Zig, Bash (functions) and Markdown (headings) have one; CSS, HTML, JSON, SQL, XML and YAML have none, so they have no symbols.

The contract: `@name` captures the symbol's name, and `@definition.<kind>` captures the whole declaration, where the kind is one of `function`, `prototype`, `type`, `struct`, `enum`, `macro` and `heading`. A pattern may also capture `@body`. A symbol's signature is the declaration's text up to its first `body` field (at any depth, so `const f = (a) => {` stops at the arrow function's body) or its `@body` node, with comments left out, blanks and line breaks collapsed to single spaces, and cut to `maxSignatureLength` (512 bytes). `@body` is for declarations whose grammar has no `body` field: a Go struct stops at its field list, a Zig container and a Go interface at their `{`, and a setext Markdown heading at its underline. In C, a `typedef struct Name {...} Name;` gives both a `struct` (`struct Name`) and a `type` (`typedef struct Name`), as ctags does, and declarators are matched to two pointers deep (`char **f(void)`). A Go type is its `type_spec`, as one `type (...)` can hold several. A JavaScript function given to a name with `const`, `let` or `var` counts as a function. PHP and JavaScript classes, PHP interfaces and traits, and Go interfaces and other named types are `type`; Zig structs, unions and opaques are `struct`.

`HighlightSymbols` runs the tags query over the buffer's own tree (not injected layers, so code blocks in Markdown add none), parsing first if the buffer changed. Matches are sorted by where the definition starts, and a definition that several patterns match is visited once, for the earliest pattern. `HighlightSymbolsOfText` does the same for text in one piece with a parser of its own under the same `maxParseTime` deadline, for files that are not open, and gives the same symbols as the live buffer (checked over every file in `src/`). A buffer whose highlighting is off has no symbols. Listing the 900 symbols of a 15,000 line C file takes about 20 ms once it is parsed.

Every function, prototype, struct, union, enum and typedef in `src/` is found with the declaration's text as its signature, checked against a ctags-style scan of the sources.

### Project symbols

`symbols` keeps an index of the symbols of every loaded file whose language has a tags query, for Alt-D, Alt-Shift-D and Alt-Shift-S. Each symbol is its entry's serial, its kind, its name's range, and its name and signature in one shared string. The symbols are sorted by name (then serial and position), so the symbols of a name are found by binary search. Each indexed file records its serial, its language, and where its symbols came from: an open document at a buffer revision, or the file on disk at a `FileStamp`. Finding a file's symbols again bumps its generation instead of removing the old ones; new symbols are appended unsorted, and before each lookup a merge sorts them into the rest and drops those whose file is gone or whose generation is old, packing the strings once most of them are left over. So an edit in one open buffer costs one parse of that buffer and a linear merge, not a sort of the whole index.

The index is built the first time a command needs it, by a scan of every loaded entry that is not open, named, not refused, and either has a language with symbols by its path or has no extension (its `#!` line decides). Before each lookup, the files of removed entries are dropped and every open document whose revision (or language, after a rename) differs from the one indexed is indexed again from its live tree with `HighlightSymbols`, so a function written and not saved is found. The entries that are not open are read by the scan and parsed with `HighlightSymbolsOfText`. A file with nothing to find is recorded too, so it is not read again. When a name is not found in a complete index, a second scan reads only the entries whose stamp changed (the others cost a `stat`), then the lookup runs once more before reporting "not found". Esc stops either scan and keeps what was indexed; the index counts as complete only after a scan that went through every file, so the next command scans again, reading only what is not indexed yet. A folder opened with Ctrl-O drops the index (serials would make its symbols miss anyway; this frees them). A command waits for the scan by leaving what it wants (the name, the window width) pending, and the scan's `finish` runs it.

Lookups consider only symbols that code can name (not Markdown headings), in the current buffer's language when it has any, with the current file's first, and a `typedef struct` counts once. Alt-D takes the word at the cursor. The targets are its definitions (every kind but `prototype`), or its prototypes when there is no definition, or when the cursor is on the name of a definition (then the other definitions when there is no prototype), leaving out the one the cursor is on. One target is jumped to (its name's start, clamped); several open a picker of `file:line  kind` with the signature as the note and a preview. Alt-Shift-D tries the word at the cursor, then the name before the innermost unclosed `(` to the left on the line, and shows the first that has symbols: the current file's, else a prototype, else the first. The signature is cut with `…` to the window width, and its `file:line` follows when there is room. Alt-Shift-S lists every symbol as `name  kind` with `file:line` as the note, with the preview (which hides the notes, so its header names the file instead), starting on the first symbol named by the word at the cursor.

Every call to a project function in `src/*.c` (3,872 call sites) goes where a ctags-style baseline of the sources says: straight to the only definition, to a picker when there are several, and to the prototype from the definition.

### Syntax selection

`HighlightNodeAround` finds the smallest named node that holds a range and is larger than it, in the buffer's tree or in an injected layer that is parsed and not edited since (so inside a fenced code block the code's own nodes count), taking the smaller of the two. Alt-Right grows every cursor's selection to that node, anchor at its start and head at its end, and merges cursors that meet. Without a tree (no grammar, or highlighting off) it selects inside the closest brackets as Ctrl-M does, collapsing to the primary cursor.

Each Alt-Right pushes a copy of the cursor set before it onto a stack in `move`, and remembers the view, the buffer's revision and the cursors it left. Alt-Left pops the last copy back, but only while all three are unchanged: any movement, edit (including one in the other view of a split) or other command that changes the cursors makes the stack stale, and the next Alt-Right or Alt-Left starts again.

### Selection edges

Ctrl-Shift-Up and Ctrl-Shift-Down move the top or bottom edge of every selection outward by a line, and Alt-Shift-Down and Alt-Shift-Up move them inward (`MoveSelectionEdge`). They work on logical lines, not visual rows, because the edges are line boundaries: the top edge only ever lands on a line start and the bottom edge on a line end, and each press takes an edge to the next such boundary. So the first press of an edge in the middle of a line goes to that line's start or end, which is what trims the brace lines from a Ctrl-M selection. Each selection keeps its direction (a cursor with no selection ends with its head at the bottom). An edge never passes the other one, so a shrink that would leave nothing leaves that cursor alone, and growing stops at the ends of the buffer. Cursors that meet are merged.

### Spell check scope

Painting `literal` or `uri` also sets a sticky literal flag that later paints do not clear, so the contents of a code block stay marked as code even though `@none` and the injected language recolour them. A `string.special` capture (a CSS colour, a regular expression, a JSON key) sets a special flag. Spell check passes over literal and special bytes, and otherwise looks at comments and strings in every language, and in prose languages also at uncoloured text and markup (headings, emphasis, link text).

## Git

### Reading a repository

`git` is the editor's own reader, not the `git` program or a library, and does only what the change marks need: find the text of one file in the commit HEAD names. It never writes, and it never hashes: every object is looked up by a name read from a ref, a commit or a tree, so SHA-256 differs from SHA-1 only in the length of a name (32 bytes rather than 20), which `extensions.objectformat` in `.git/config` gives.

`GitRepoOf` takes the real path of the file's folder and walks up to the first `.git`. A `.git` folder holding `objects` is a repository; a `.git` file (a worktree or a submodule) ends the walk with none, since the folders above belong to a repository that does not track these files. `.git/config` is read for three settings: `core.bare` and `extensions.refstorage=reftable` refuse the repository, as does an object format other than `sha1` or `sha256` or a `repositoryformatversion` over 1. Repositories are kept, readable or not, until the editor exits, so a `GitRepo *` never dangles, and the last folder looked up is remembered, as files come a folder at a time. A path inside `.git` is not in the work tree.

HEAD is `ref: <name>` (followed up to five times, only under `refs/`) or a name in hex. A ref is read from its own file, or else from its line in `packed-refs`. The stamps of `HEAD`, the branch's file and `packed-refs` are kept, so `GitHead` only reads the refs again when one of them changed, which costs three `stat` calls. A branch with no commits has no ref file, and its path is stamped so the first commit is noticed.

An object is looked for in the packs first, then as a loose file (`objects/xx/...`, inflated, then split at the nul after `<type> <size>`), and when both miss the pack folder is listed again, as a fetch or `gc` writes new packs. Each pack index (version 2: a fan out table, sorted names, checksums, 32-bit offsets and a table for larger ones) and its pack are mapped with `mmap` and found by binary search. A pack entry starts with its type and size; a delta names its base by a backwards offset in the same pack or by object name (looked up in every pack, or loose). The chain of deltas is followed down to a whole object (at most 10,000 deep), which is inflated, and the deltas are applied from the bottom up (copies from the base and inserted bytes). The last 32 objects rebuilt this way (each up to 4 MB) are kept by pack and offset, and so is each chain's base, so the trees above a file and a base that many deltas share are not rebuilt for every file. The commit's `tree` line gives the root tree, and each name of the path is found among `<mode> <name>\0<name in binary>` entries: a folder (`040000`) goes down a level, and a regular file (`100644` or `100755`) is the blob. A link, a submodule or a missing name counts as untracked.

So the editor reads a fresh clone (one pack, mostly deltas), a repository after `gc --aggressive` (long chains), packed refs, a detached HEAD and SHA-256 repositories; each was checked by comparing every tracked file with `git show HEAD:<path>`. A partial clone's missing objects, an index of version 1 and anything `git` itself would need filters for (LFS, `eol` conversion) are outside it: a missing object leaves the file without marks, and a filtered file shows as changed.

### Changes

A document gets its `Changes` when it opens with a path, and again when a save or rename gives it another path. The committed text is split into lines at `\n`, leaving out a `\r` before it as `preview` and project search do, since a buffer holds its lines without either. It is read again when HEAD names another commit, which `ChangesRefresh` checks when the document is switched to, reloaded or saved, and when the panel or the changed files picker opens. A file the commit does not have still gets its `Changes`, without hunks, so a commit that adds it starts its marks.

Changes do not listen to the buffer. `ChangesHunks` keeps the buffer revision its hunks were worked out at and works them out again when asked after it changed, which the first gutter mark of a frame does, so a burst of edits costs one diff. Buffers and committed texts over `maxDiffSize` (16 MB) get no hunks. `ChangesMarkOf` finds a line's hunk by binary search: lines in a hunk with no old lines are added, other lines in a hunk are modified, and a hunk with no new lines (a removal) is marked on the line after it, or on the last line when it removed the end of the file. Hunks are never adjacent (`diff` joins them), so each line has at most one mark. The counts treat a hunk of o old and n new lines as min(o, n) lines changed and the rest added or removed.

`diff` compares lines by their bytes. It passes over the common start and end directly (no copies, through a callback per line), gives the lines in between ids from a hash table, and runs Myers' algorithm on the ids, searching from both ends for the middle of a shortest edit script and dividing there, with the common start and end of each part passed over again. The search keeps one pair of arrays, sized for the whole, as each division finishes with them before the parts are compared. A part whose edit distance passes `maxDiffCost` (1024) is reported as one hunk, so unrelated texts take time bounded by the cost rather than the size. The added and removed totals equal those of `git diff --minimal` over random edits of every `.c` file in `src/` (one exception by design: a file that loses its final line break; git counts the last line as changed, while here the empty line after it is removed).

### Display

The gutter's first cell, before the number, holds the mark, so marks need line numbers on and never move the text. A changed line's bar is drawn beside every one of its rows when wrapped; a removal's mark only beside the first. The status bar shows the counts in its full form, before the wrap state.

The change panel is drawn by `review` into the right half of the window, beside the focused pane, through a `FramePanel` function in the frame, the shape of a picker's preview. It takes the place of a split without changing it, and below `minSplitWidth` it is not drawn, so closing it or widening the window brings back what was there. Each frame it finds the hunk at the primary cursor and draws its header (`file:line +a ~c -r`), three lines of context from the buffer, the old lines from the committed text on a red background and the new lines on a green one, numbered by their own side, then three lines of context, scrolled when that is taller than the panel so the cursor's line shows.

Ctrl-G runs a scan of every named, unrefused entry: open documents use their own changes, and the others are compared from the text the scan read with `ChangesOfText`, which reads their committed text for the occasion. The picker marks entries as the buffer pickers do, and notes each one's counts (shown when there is no preview). Its preview is the whole file as a diff: every line of the newer text, with each hunk's committed lines before its new ones, drawn by the same row function as the change panel. The rows are never built: the row each hunk's old lines start on is the hunk's new start plus the old lines of the hunks before it, so a binary search over those tells what any row shows, and a draw costs the hunks plus the rows shown. A file that is not open is read again from disk when it is selected and compared through `ChangesNewText`, changes whose newer side is that text rather than a buffer, kept until another item is selected or the picker closes. The preview keeps its own top row, placed at the first change, and takes Shift with the arrows and pages to scroll and Alt-Shift-] and Alt-Shift-[ to step through the changes through the picker's key handler; the change it shows is the step's, or else the first that ends below the top, and Enter opens the file at that change as it is then.

### Restoring a change

Alt-Z takes the hunk at the primary cursor's line from `ChangesHunkAt`, so a removal is restored from the line its mark is on, and replaces the hunk's new lines with its old ones from the committed text, in one undo group. The hunk is copied first, as the edit makes the hunks stale. Lines are replaced with the line break after each, which a hunk that runs to the end of the buffer does not have: there the range starts at the end of the line before the hunk and the old lines go after a line break (or with none, from the start of the buffer, for a hunk that starts at the top), and an addition at the end goes with the line break before it. Both sides end with the same empty line when the file ends with a line break, so this also covers a file that lost or gained its last line break. Only that hunk changes, and the cursor goes to its start.

## Performance

Measured on the release build, timed from the key to the end of the frame:

- A 100 MB file of 1.3 million lines loads in about half a second. Moving, typing, paging and undo each take under 10 ms. Indenting every line takes 0.3 seconds, and spell check (which counts every unknown word) about 3 seconds.
- A 17 MB line without soft wrap takes about 35 ms a key, and with soft wrap 5 to 75 ms (more right after an edit, when its rows are laid out again).
- Tree-sitter highlighting is skipped above 16 MB, and stops for a buffer whose parse takes over a second (a 7 MB minified file does after its first edit). The first edit after parsing a 3 MB Markdown file pauses for about 0.3 seconds, and typing in a 2,000 line fenced block costs about 35 ms, because the Markdown grammar scans the whole block again.
- 100,000 files load and draw the picker in about 60 ms from the page cache, filtering them takes 2 to 4 ms a key, and searching them all takes about 0.35 seconds.
- An edit with 1,000 cursors takes 4 to 22 ms, and with 10,000 about 0.2 seconds (see Multiple cursors).
- Comparing a 15 MB file of 330,000 lines with its committed text takes about 25 ms with one line changed, and about 85 ms with 330 changes spread through it (release build, reading both files included). Reading a file from a pack takes about 3 ms for a source file, and about 40 ms for the 3.9 MB C grammar `parser.c` or the 17 MB SQL one, as inflating is done a bit at a time.
- Indexing the symbols of `src/` (about 100 files) and resolving all 3,872 calls in it takes 0.5 seconds. The 99,600-file tree of random C keywords (390 MB) indexes in about 170 seconds, about 2 MB/s, because tree-sitter's error recovery is slow on such text; Esc stops it within 0.1 seconds, and once the index is complete a lookup takes under 0.1 seconds.

## Comments

Ctrl-/ uses the comment markers from `lang`. It first decides for all the lines touched by every cursor: when each of them that is not blank is commented already, it uncomments, otherwise it comments. Commenting puts the start marker and a space at the smallest indentation of each block of touched lines (so the markers line up) and, for block comment languages, a space and the end marker at the end of the line. Blank lines are left alone unless every touched line is blank. Uncommenting removes the markers and one space next to each. It runs as line edits like indentation (one replace per line, in a second pass for end markers), so other views keep their cursors on the same text, and the whole toggle is one undo step.

## Conventions

- Types are `PascalCase` and structs are typedef'd (`StrBuf`). Enum constants are `PascalCase` prefixed with their enum name (`CursorStyleLine`, `GraphemeBreakExtend`).
- Functions are `PascalCase` and prefixed with their module name (`StrBufAppend`, `MemoryResize`). Variables and constants are `camelCase`.
- Headers use `#pragma once`.
- C23 features in use: `bool`, `nullptr`, `constexpr`, `[[attributes]]`, `<stdckdint.h>`, digit separators.
- Vendored code is compiled with `-w` and never edited. Queries the editor needs that upstream does not provide in the right form (the tags queries) and the `language` files live in `languages/`, outside `vendor/`. Strict warnings (`-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Werror`) apply to `src/` only.

## The default packages

`./build.sh --languages` builds a package for every folder in `vendor/grammars/`: the grammar's `parser.c` and `scanner.c` compiled with `-fPIC` and linked as `parser.so`, the vendored `highlights.scm` and `injections.scm` (PHP's two upstream injection files, `injections.scm` and `injections-text.scm`, joined into one), and the files in `languages/<id>/`. `--install` copies each file next to its target and renames it into place, so an editor that has the old `parser.so` loaded keeps its copy. Grammar objects are rebuilt only when something in the grammar's folder is newer, as the runtime is.

With the grammars out of the binary, the editor went from 9.7 MB to 1.6 MB, and with the word list read from the config folder too, to 0.6 MB (0.3 MB of it the tree-sitter runtime). The packages take 8.1 MB: SQL 2.4 MB, Bash 1.4 MB, PHP 1.1 MB, Zig 0.7 MB, C 0.6 MB and the rest under 0.5 MB each. Reading all fourteen `language` files at startup takes well under a millisecond, and each grammar is opened only when a file of its language is.

## Unicode tables

`src/unicodedata.c` is generated and committed. To regenerate it, for example for a new Unicode version:

1. Download `UnicodeData.txt`, `EastAsianWidth.txt`, `CaseFolding.txt`, `auxiliary/GraphemeBreakProperty.txt` and `emoji/emoji-data.txt` from `https://www.unicode.org/Public/<version>/ucd/` into one folder.
2. Run `tools/unicodedata.py <folder> > src/unicodedata.c`.

Case folding (for search, sort and pickers) uses the `C` and `S` entries of `CaseFolding.txt`, and case conversion uses the simple upper and lower case mappings in fields 12 and 13 of `UnicodeData.txt`. The full and context dependent mappings of `SpecialCasing.txt` (`ß` to `SS`, final sigma, Turkish and Lithuanian rules) are not used. The current tables are Unicode 16.0.0. Width rules: East Asian Wide and Fullwidth are 2 columns. Nonspacing marks, enclosing marks, format characters (except the soft hyphen), Hangul medial vowels and final consonants, and U+200B are 0. Everything else is 1.
